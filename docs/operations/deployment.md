# Linux deployment and rollback

Status: templates provided, installation and acceptance on a clean Linux server pending. No services were installed and no real database was contacted. One instance, modular monolith, Nginx same-origin SPA + /api/v1; no Redis/JWT/Kafka dependency. Release is blocked by ADR-001, incomplete acceptance and external security/restore gates.

1. Freeze supported exact versions and image/JAR/frontend hashes in release manifest after compatibility/security evidence. Install patched Java21, MySQL8.4 LTS, Nginx (ssl_reject_handshake support), age and backup tools from approved packages. Verify trusted TLS chain and DB CA/hostname. Restrict public ports to80/443 and administrator access; DB private-only,8080/8081 loopback.
2. Create `task-workbench` system user with no shell/home login. Create `/opt/task-workbench/releases/<release>` root-owned and immutable to the app; `/var/lib/task-workbench/attachments` app-owned0700; `/etc/task-workbench` root0700. Use encrypted local/temporary backup storage. Do not grant app write permission to code or secrets.
3. Build with `mvn -B -ntp -f backend/pom.xml verify`, frontend `npm ci && npm run build` (after lint/typecheck/tests). Copy the final executable JAR to `<release>/backend/task-workbench.jar`, frontend/dist contents to `<release>/frontend`, scripts/ to `<release>/scripts`. Set shell scripts0755. Store artifact SHA256/SBOM externally. Verify JAR was not built with offline-verification.
4. DBA edits `deploy/mysql/accounts.sql.template`, resolves every placeholder and applies on a new approved test database first. Do not feed unedited template to mysql. Application identity has only DML. Separate migration identity has DDL only on this schema and is locked except during migration. Use encrypted transport; configure `deploy/mysql/server.cnf.example` against actual private DB listener and approved binlog retention. Check least privilege by proving runtime CREATE/DROP is denied.
5. Copy/edit prod.env.example into root0600 `/etc/task-workbench/runtime.env`. Every secret must be independently generated; real bootstrap policy and TOTP-key format must match backend validation. Never source or commit this file. Keep migration credentials out of it. Runtime Flyway is disabled. Execute `validate-prod-env.sh` under that service environment as part of startup; this validates structure, not Java patch approval.
6. Stop application, take verified consistent backup and record version/schema. Run Flyway once with restricted temporary migration identity using the **same reviewed migrations and frozen Flyway version** (Flyway CLI or controlled migration job), validate checksums, then lock identity/remove temporary file. `migration.env.example` is configuration only, not an automatic migrator; do not start an ordinary application as an unbounded migration job. MySQL DDL may auto-commit; there is no assumed migration rollback. Test old-version compatibility explicitly.
7. Before first production login, use the explicit `provision` profile in an approved one-off job on the migrated empty database with external TASK_BOOTSTRAP_PASSWORD/TASK_BOOTSTRAP_ACCOUNT/TASK_BOOTSTRAP_COMPANY_NAME/TASK_BOOTSTRAP_COMPANY_CODE. It creates only an initial company, administrator and original KPI template; ordinary prod startup does not seed. Stop the job, remove bootstrap secrets and use prod runtime thereafter. The initial administrator must change password and enroll TOTP. Production leadership/role membership provisioning must also be explicitly approved and verified before business use; this minimal provisioner is not a complete privileged account-management workflow. Never use demo/test/bootstrap synthetic fixture profiles in production.
8. Install systemd unit; set `/opt/task-workbench/current` symlink atomically to reviewed release. Install edited Nginx template. Set actual fixed domain/certificate paths in all places; `nginx -t`, `systemd-analyze verify`, then daemon-reload/start and test in isolated staging. Never serve attachments from the SPA directory. Security headers must cover API errors too. Vite's development proxy is local-only.
9. Verify readiness locally8081 (no details externally); unauthenticated APIs, CSRF/TOTP/session revocation and role scope; Nginx headers/unknown Host/forwarded-header spoofing; 10MB/11MB limits; privacy of logs; quarantine failure; permissions; backup/restore; restart recovery. Only then enable HSTS after domain/TLS/browser confirmation.

Rollback: preserve encrypted backup, binaries, migrations and manifest before rollout. On failed health/security verification stop writes and workers; change current symlink to prior compatible artifact and restart only after schema compatibility proof. Never edit/checksum-repair historical migrations to hide failure. If schema is incompatible, restore a consistent DB+attachment batch into an isolated replacement environment, replay approved binlogs, reconcile, then switch traffic under an approved downtime plan. Keep failed instance read-only for investigation. No automatic destructive rollback script is provided.

Logs: service logs go to journald; configure persistent journal with bounded disk limits and off-host immutable security/business audit shipping. For example site-local journald retention must implement approved ADR-005 rather than deleting KPI history. Alerts for disk usage, backup age, unsuccessful service restart and lost log forwarding are mandatory. Do not log full request bodies, Cookie, credentials, TOTP, Webhooks or attachments.
