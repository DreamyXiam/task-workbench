# Encrypted backup, binlog PITR and recovery drill

Status: scripts are dry-run by default; isolated MySQL8.4 + attachment restore is **not executed**. RPO/RTO numerical targets require ADR-006 business approval. Do not describe daily backups as an agreed RPO. Record actual last archived binlog time and restoration duration in each drill.

Daily full backup: approved maintenance window stops the only application instance and its embedded jobs, ensuring no application transaction or file mutation is active; prohibit every external writer/migration during the entire snapshot. `backup.sh` dumps database with source binlog coordinate, copies immutable attachments, computes per-file/database checksums, gives both a UTC batch ID, encrypts the tar stream with age, then restarts the previously active app through an EXIT trap. Failure leaves a non-final `.partial` encrypted artifact, never a successful batch. Batch manifest and hashes are inside the encrypted payload. Plaintext temporary data requires an encrypted disk; storage-device secure erasure is not assumed. Do not use this quiescence procedure when external writers cannot be stopped.

Credentials: root0600 MySQL option file contains `[client]`, user=task_backup, password supplied privately, host/port and ssl-mode=VERIFY_IDENTITY plus CA. Never put password on CLI. Private age identity stays off the backup host; public age recipient may be present. DBA tests `deploy/mysql/accounts.sql.template` grants against exact MySQL8.4 patch. Backup identity has no production writes, FILE, SUPER or application DDL. No retention deletion is automated pending ADR-005.

On approved Linux host, review paths then run (first command performs no service/database operation):

```bash
bash scripts/backup.sh
sudo -i
export BACKUP_APPROVED=yes MYSQL_BACKUP_CNF=/etc/task-workbench/backup.cnf
export AGE_RECIPIENT='<public-age-recipient>' BACKUP_ROOT=/srv/encrypted-task-backups
bash /opt/task-workbench/current/scripts/backup.sh --execute
```

Copy final `.tar.age` and its checksum to restricted off-host/offline storage; verify checksum and immutable retention there. Alert on failed backup, excessive backup duration, app restart failure or stale successful batch. Test that the backup directory is writable only by its owner. Configure a daily approved root-owned scheduler after a measured staging drill; do not embed secrets in its command line.

Binlogs: require ROW, full images, sync_binlog1, durable redo and log_bin. Archive frequently enough for the **approved** RPO. A DBA rotates a log and obtains `SHOW BINARY LOG STATUS`; only earlier CLOSED files may be passed to `archive-binlog.sh`. After `BINLOG_CONFIRMED_CLOSED=yes`, set CLOSED_BINLOG, AGE_RECIPIENT and BINLOG_ARCHIVE_ROOT and run `bash scripts/archive-binlog.sh --execute`. Default is dry-run. Preserve contiguous numeric files spanning every retained base coordinate, checksums and encryption keys; copy off-host, verify decryptability and alert on sequence gaps. Local binlog expiry may only remove files proven archived and no longer needed by any retained base. Never archive a changing current file or automatically purge based only on age.

Isolated base restore:

1. Create a disposable **separate MySQL server**, block all production connectivity/outbound Webhooks, and create an empty schema named `task_restore_<drill>`. Give a dedicated restore identity rights only on that schema; no production privileges. Keep application/jobs stopped. Inventory restore host/endpoint/schema, age identity escrow authorization and chosen base batch.
2. Verify transported ciphertext SHA256. Put client options in0600 file. Set ISOLATED_RESTORE=yes, RESTORE_DATABASE=task_restore_<drill>, RESTORE_MYSQL_CNF, RESTORE_DIRECTORY to a new directory on encrypted disk, BACKUP_FILE and AGE_IDENTITY_FILE. Run `bash scripts/restore-isolated.sh` to see dry-run; review, then add `--execute`. It rejects non-isolated schema names, nonempty targets and unsafe tar members, verifies hashes, imports base and leaves attachments for reconciliation. A failure leaves the isolated destination for investigation; use a new destination/schema for another attempt.
3. Verify database encoding/schema/Flyway checksum and attachment row-to-object mapping. Record quarantined files separately; they remain unavailable. A hash success alone does not prove business consistency.

PITR (manual review required; never pipe binlogs into production): decrypt needed CLOSED binlogs on encrypted isolated storage. Use matching MySQL8.4 `mysqlbinlog --verify-binlog-checksum --base64-output=DECODE-ROWS --verbose` for **inspection only**. Find base's source log/position in database.sql; determine final target by transaction/GTID boundary before the destructive event. UTC/timezone and DST must be recorded. `--stop-datetime` alone is insufficient proof that the desired transaction boundary was selected.

For replay, use normal executable `mysqlbinlog` output (without DECODE-ROWS), ordered complete files, first-file `--start-position=<base-position>` and last-file reviewed `--stop-position=<transaction-end-position>`. Restore on a dedicated server with **the original task_workbench schema name** if binlogs reference it; the helper's renamed schema is suitable for base verification but is not an automatic PITR rewrite. Do not rely on `--database` or text replacement to isolate row/statement events. A DBA must create a separate reviewed original-name restore on the disposable server before replay. Disable replication, scheduled jobs, event_scheduler and network delivery there. Review the SQL event stream and schema names first, apply with an isolated account, record applied GTIDs/positions and error-free end marker. Recheck FK/data integrity, tasks/timeline/current and historical deadlines, KPI snapshot raw totals/template hashes, audit continuity, attachment existence/version/SHA256, and outbox state without sending notifications. Use paired attachments from the base; replayed attachment metadata may reference post-base files, so a PITR point after the base requires matching continuously archived immutable attachment objects. **Without post-base attachment archive, PITR is limited to the base consistency point.** Use `archive-attachments.sh` for encrypted immutable-object snapshots and schedule them to the approved RPO; it archives without deleting. Verify every target-point referenced object exists and hashes match before claiming later-point recovery.

Drill record: start/end/timezone, operators, isolated endpoint, exact tool versions, chosen batch and binlog range, attachment-object archive range, intended/actual recovery point, measured RPO and RTO, row/hash/business/KPI comparisons, missed or duplicate delivery risk, failures, evidence paths and sign-off. Restore success and production cutover are separate authorizations. Delete drill plaintext under approved secure-storage policy after evidence preservation; never change production retention during a drill.
